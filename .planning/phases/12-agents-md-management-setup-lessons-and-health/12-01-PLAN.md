**Frontmatter:**
```yaml
---
description: "Analyze codebase and generate a minimal, high-value AGENTS.md"
argument-hint: "[project-path]"
tools:
  read: true
  glob: true
  grep: true
  write: true
---
```

No `bash` tool — this is pure analysis + file generation per requirements.

**Body structure — use `<objective>`, `<process>`, `<output_format>` sections:**

The `<objective>` should explain: Analyze the project's actual codebase and generate a minimal AGENTS.md containing only what agents CANNOT infer from reading the code itself. Target 20-40 lines, absolute max 60.

The `<process>` should instruct Claude to:

1. **Detect build/test/lint commands:**
   - Read `package.json` scripts, `Makefile` targets, `Cargo.toml` commands, `pyproject.toml`, etc.
   - Extract exact commands: build, test (full + single-file), lint, typecheck, dev server
   - Check for file-scoped variants (e.g., `vitest run path/to/test.ts`, `eslint path/to/file.ts`)

2. **Detect framework + key dependencies:**
   - Read dependency files for framework, language version, key libraries WITH versions
   - Only include what matters for agent context (not every transitive dep)

3. **Map directory structure:**
   - Read top-level directories and identify what lives where
   - Keep brief — agents can `ls` themselves, just note non-obvious conventions

4. **Read existing configs:**
   - Check for `.eslintrc*`, `.prettierrc*`, `tsconfig.json`, `biome.json`, etc.
   - Specifically instruct: if a linter/formatter enforces a rule, do NOT duplicate it in AGENTS.md

5. **Check for existing agent instruction files:**
   - Look for `AGENTS.md`, `CLAUDE.md`, `.cursorrules`, `.github/copilot-instructions.md`
   - If found, incorporate relevant content (don't start from scratch)

6. **Generate AGENTS.md** with exactly this structure:
   ```markdown
   # AGENTS.md

   ## Commands
   (exact build, test, lint, typecheck, dev commands)
   (file-scoped variants where possible)

   ## Stack
   (framework, language, key deps WITH versions)

   ## Structure
   (top-level dirs and what lives where — brief)

   ## Boundaries
   (do NOT rules: files to never modify, patterns to avoid)
   ```

7. **Write the file** but do NOT commit — leave as unstaged change
8. **Print summary** of what was generated and why each section was included

**Key constraints to encode in the prompt:**
- Only include what the agent CANNOT infer from reading the code itself
- Never duplicate what linters/formatters already enforce
- Target 20-40 lines; if over 60, the prompt should instruct Claude to trim
- Never auto-commit — always leave for human review
- If existing AGENTS.md/CLAUDE.md found, note what was incorporated vs. new

**Frontmatter:**
```yaml
---
description: "Extract actionable lessons from recent build sessions into a candidate buffer"
argument-hint: "[project-path]"
tools:
  read: true
  glob: true
  grep: true
  write: true
---
```

No `bash` tool — pure analysis + file generation per requirements.

**Body structure — use `<objective>`, `<process>`, `<output_format>` sections:**

The `<objective>` should explain: Read the project's recent build history and extract specific, actionable lessons — things that would prevent future failures or reduce wasted cycles. Write to a candidate buffer for human review.

The `<process>` should instruct Claude to:

1. **Read recent build history:**
   - Glob `.planning/phases/*/` for recent phase summaries (especially `*-SUMMARY.md` files)
   - Look for failure notes, deviation sections, workaround descriptions
   - Read recent `*-VERIFICATION.md` files for patterns of what failed and why
   - Check `STATE.md` for accumulated decisions and concerns

2. **Identify patterns:**
   - Repeated failures (same tool/library/pattern failing across phases)
   - Workarounds that were applied (signal: the obvious approach didn't work)
   - Configuration gotchas discovered during execution
   - Commands or flags that aren't obvious but were needed

3. **Extract actionable lessons:**
   - Each lesson must be specific and actionable, not generic
   - Good example: "vitest requires `pool: 'forks'` and `maxForks: 1` in this project to avoid OOM"
   - Bad example: "Always write comprehensive tests"
   - Format each as: one-line summary + brief context (1-2 sentences)
   - Mark each as `- [ ] pending review`

4. **Cross-reference with existing AGENTS.md:**
   - If AGENTS.md exists, read it
   - Skip any lesson that duplicates existing AGENTS.md content
   - Note in output which lessons are net-new vs. refinements

5. **Write to `.planning/LESSONS-CANDIDATES.md`:**
   - Use a clear format with date, source phase(s), and candidate list
   - Include a header explaining this is a buffer file for human review
   - NEVER auto-commit to AGENTS.md

6. **Print the candidates** for immediate human review

**Key constraints to encode in the prompt:**
- NEVER auto-commit lessons to AGENTS.md — always a candidate buffer
- Lessons must be specific (not "write good tests" but "vitest needs pool: forks for this project")
- Cross-reference existing AGENTS.md to avoid duplicates
- Focus on non-obvious knowledge that prevents future failures
