---
description: "Extract actionable lessons from recent build sessions into a candidate buffer"
argument-hint: "[project-path]"
tools:
  read: true
  glob: true
  grep: true
  write: true
---

<objective>
Read the project's recent build history and extract specific, actionable lessons — things that would prevent future failures or reduce wasted cycles.

Lessons are written to `.planning/LESSONS-CANDIDATES.md` as a buffer file for human review. NEVER auto-commit to AGENTS.md.

Every lesson must be specific enough that a different developer (or agent) could act on it without asking follow-up questions.

Good lesson: "vitest requires `pool: 'forks'` and `maxForks: 1` in this project to avoid OOM"
Bad lesson: "Always write comprehensive tests"
</objective>

<process>

<step name="read_history">
## 1. Read recent build history

Scan the planning directory for execution evidence:

```
glob(".planning/phases/*/*.md")
```

Focus on these files in priority order:

1. **SUMMARY.md files** — Read the "Deviations from Plan" and "Issues Encountered" sections. These are the richest source of lessons.
2. **VERIFICATION.md files** — Check what passed vs. failed, and any notes about why.
3. **STATE.md** — Read the "Decisions" and "Concerns" sections for accumulated project-level knowledge.

Read the most recent 3-5 phases. Older history has diminishing returns.
</step>

<step name="identify_patterns">
## 2. Identify patterns worth capturing

Look for these signal categories:

**Repeated failures:**
- Same tool, library, or pattern causing problems across multiple phases
- Configuration that had to be discovered through trial and error
- Commands or flags that aren't obvious but were required

**Workarounds applied:**
- Places where the obvious approach failed and a workaround was needed
- Any "we tried X but had to use Y because..." patterns
- Framework-specific gotchas that aren't in official docs

**Configuration gotchas:**
- Environment variables that are required but not obvious
- Config file settings that deviate from defaults
- Tool interactions that cause unexpected behavior (e.g., linter + formatter conflicts)

**Execution patterns:**
- Test runner requirements (pool settings, isolation, timeouts)
- Build tool quirks (watch mode issues, cache invalidation)
- Deployment-specific knowledge (env var naming, platform constraints)

Skip anything that is:
- Generic advice any developer would know
- Already enforced by linters, formatters, or CI checks
- Obvious from reading the project's README or docs
</step>

<step name="cross_reference">
## 3. Cross-reference with existing AGENTS.md

Check if AGENTS.md exists:
```
glob("AGENTS.md")
glob("CLAUDE.md")
```

If found, read it and compare each candidate lesson:
- **Duplicate:** The lesson is already captured in AGENTS.md — skip it
- **Refinement:** The lesson adds specificity to an existing AGENTS.md entry — mark as "refinement of existing"
- **Net-new:** The lesson covers something not in AGENTS.md — mark as "new"

This prevents the candidate buffer from accumulating duplicates over repeated runs.
</step>

<step name="extract_lessons">
## 4. Extract actionable lessons

For each lesson, write:
- **One-line summary:** Terse, actionable, starts with a verb or noun
- **Context:** 1-2 sentences explaining when this matters and what goes wrong without it
- **Source:** Which phase/summary the lesson came from
- **Status:** `- [ ] pending review`

Quality bar for inclusion:
1. Is it specific to THIS project? (not generic industry knowledge)
2. Would knowing this PREVENT a future failure or save significant time?
3. Can an agent ACT on it without further clarification?

If any answer is no, do not include it.
</step>

<step name="write_buffer">
## 5. Write to candidate buffer

Write (or append to) `.planning/LESSONS-CANDIDATES.md`:

```markdown
# Lessons Candidates

> This is a buffer file for human review. Lessons here are NOT active —
> they become active only when a human moves them to AGENTS.md.
> Generated by `/gsd-lessons` — safe to delete or regenerate.

## Candidates from [date]

Source phases: [list of phases analyzed]

### Net-new lessons

- [ ] **[one-line summary]**
  Context: [1-2 sentences]
  Source: [phase/summary reference]

- [ ] **[one-line summary]**
  Context: [1-2 sentences]
  Source: [phase/summary reference]

### Refinements to existing AGENTS.md entries

- [ ] **[existing entry] → [proposed refinement]**
  Context: [why the refinement matters]
  Source: [phase/summary reference]
```

If the file already exists from a previous run, append a new dated section rather than overwriting. This preserves the review history.

**Do NOT commit this file.** It is a buffer for human review only.
</step>

<step name="print_candidates">
## 6. Print candidates for review

After writing, print all candidates to the console:
- Group by "net-new" vs. "refinement"
- Include the full context for each
- Note the total count and which phases were analyzed
- Remind the user: "Review these candidates. Move approved lessons to AGENTS.md manually."

If no actionable lessons were found, say so explicitly:
"No actionable lessons found in recent build history. This project's execution has been clean."
</step>

</process>

<output_format>
The candidate buffer should produce entries like:

```markdown
- [ ] **vitest requires `pool: 'forks'` for this project**
  Context: Default pool causes OOM errors with the current test suite size.
  Discovered in Phase 9 when test runner crashed during parallel execution.
  Source: 09-03-SUMMARY.md, Deviations section

- [ ] **`git commit --amend` breaks pilot's commit tracking**
  Context: Pilot tracks commits by hash for SUMMARY.md. Amending changes the hash
  and causes self-check failures. Use new commits instead.
  Source: 08-02-SUMMARY.md, Issues Encountered
```

Each lesson should be immediately actionable — an agent reading it knows what to do differently.
</output_format>

<guardrails>
- NEVER auto-commit lessons to AGENTS.md — this is ALWAYS a candidate buffer
- NEVER include generic advice ("write good tests", "handle errors", "use types")
- NEVER include lessons that duplicate existing AGENTS.md content (check first)
- NEVER include lessons that linters/formatters already enforce
- Focus on non-obvious knowledge that prevents future failures
- If existing AGENTS.md is comprehensive and build history is clean, report "no new lessons" — do not pad with low-value entries
- Append to existing LESSONS-CANDIDATES.md rather than overwriting
</guardrails>
